# Lessons learned (from polishing a clickable prototype, Oct 2026)

- **"For reference" means reference only**: a logo was meant to borrow another product's style, and it grew into restyling the whole site and scrapping icons already in progress. Do exactly the scope asked for; do not widen it.
- **No feature inventory once features are done**: repeated emphasis on the "feature floor" during polishing gets read as "add more features". The feature list only guards against breaking things.
- **Merge direction changes instead of overwriting**: when several directions arrive one after another, the later one usually adds to the earlier. Read them together, and if needed write one full version to replace the scattered messages.
- **Light-only means removing everything dark**: `dark:` variants, prefers-color-scheme, dark tokens, theme toggles all go, then open it once with the system in dark mode to confirm.
- **Back up demo data before testing live**: clicking through flows in a browser changes localStorage; restore a fresh demo state before finishing.
- **Do not take over the tab the user is looking at**: test in a new background tab so you do not interfere with each other.
- **The loop can stall**: scheduled wake-ups (ScheduleWakeup in Claude Code) only fire while the app is open and the computer awake, and a wakeup may fire without running. When asked "why did it stop", check that session's record before deciding whether to send a message to resume, so the same round never runs twice.
- **Self-scores are lenient**: in round 28 of a clickable prototype, self-scores gave 8 on several items, yet it still looked cheap next to award sites. Every batch uses fresh subagents who did not build it; only independent scores count.
- **Borrowing turns into copying easily**: a first-screen fill-in-the-blank sentence ended up almost exactly Linearity's structure. Originality starts from the product's own core concept (the prototype's core action should fit in one sentence); references only set the quality bar.
- **Pictures drawn in SVG look flat**: a prototype's first-screen map drawn with SVG lines and gray blocks was called "a wireframe" by reviewers. Generate pictures first; SVG is only for animation on top.
- **Overlays on generated images do not line up**: a prototype generated an illustrated map first and drew SVG routes on it afterwards; routes broke halfway, markers sat on blank ground, labels missed their places. Sketch the layout first, generate from the sketch, place overlays by code, and accept by the numbers.
- **Small fixes stall in one score band**: one prototype's independent review totals stayed at 62-67 for 38 batches. Reviewers only listed concrete problems, the developer only fixed small ones, and structural changes never got a turn. Three reviews in a row in the same band means a direction review, with a big change on a branch and an A/B.
- **Changes that raise nothing are wasted**: 38 batches of changes did not move the score. The causes: a single new reviewer's large error, "any bug caps at 6" pinning several items forever, and reviewers listing small problems without saying how to gain points. The fix: average 2 reviewers, compare with the best version so far, cap only for serious problems, write "what would add 1 point" per item, one complete list.
- **Realistic AI-looking photos cheapen a site**: a prototype's redesign B used golden-hour realistic people photos that looked very AI. Generated images avoid cinematic lighting and perfectly posed crowds; illustrations in one consistent style (maps, icons) age better, and the illustrated map version is the one that stayed.
- **Checking static pages only misses things**: a prototype's UI check claimed to cover every page, yet a person immediately saw "the highlighted card after posting has a clipped outline, icons poke out of tags, tag styles differ, subtitles repeat". States that appear only after interactions were never captured, and nothing checked clipped outlines and shadows.
- **Text-only guides leave people unable to find the button**: a prototype's guide bar only said "Next: complete the main action", and walking it by hand nobody knew what to click. Automated tests click by selectors in the code and never get stuck, so they cannot find this. Accept with a fresh subagent that only follows on-screen hints.
- **AI reviewers can all miss the same thing**: 38 batches of a prototype never lowered the review score, while a person looking said "it gets uglier every time". Lined up side by side, the version people picked actually had a higher review score. Send before/after screenshots to the user regularly; the user's eyes are the final review.
- **Winning an A/B is not finishing**: a scroll-storytelling redesign won the review and was merged and shipped, then development stopped. The goal is all 10 items at 9; the loop continues after a merge.
- **Long loops burn budget**: one prototype ran for two days and nearly used up the quota. Estimate the rounds at kickoff; when tight, scale back or hand off to a cloud session (push a branch, write a handoff).
- **Slow screenshots slow every batch**: a new headless browser per image, a fixed wait of several seconds and a full scroll each time made one batch of screenshots take minutes. Open the browser once, shoot in batches, and wait for load instead of fixed delays.
- **Test the ruler on real award sites**: on 2026-10-13 an independent reviewer scored a real Awwwards SOTD with this skill's standard. The four Awwwards items were within 0.02 of the real jury, but our 10 items averaged only 7.8, much harsher than "10 = award". It also showed that "retention" did not fit showcase sites, the originality cap hurt conceptually original sites, there was no rule for large blank stretches, and the example scores in the prompt happened to be the tested site's answer. All of this went into reviewer.md and scoring.md. After any change to the scoring standard, test again on an award site not used before.
- **Retest (same day, a different reviewer model)**: with the "award sites should score 9-10" reminder, the 10-item average rose from 7.8 to 8.3 and the four Awwwards items were 7.34 against a real 7.70, still 0.36 strict, mainly on content (treating a concept site's demo data as "not real") and usability (marking marketing sites down for having no core flow). The definitions are in reviewer.md and scoring.md. Reviewers running strict is normal, so every batch's scores must be calibrated against the anchor set before reading them.
- **Anchors realigned to real jury scores (same day, 4 SOTD samples)**: on an e-commerce and a SaaS sample, the four Awwwards items were within 0.1 of the real jury, so that scale was accurate; but real SOTDs only reached 8.3-8.6 on our 10 items. The anchors were one tier too high (Honorable Mention sat at 9). The anchors are 10 = top SOTD, 9 = average SOTD, 8 = Honorable Mention, so finishing at "all 10 items at 9+" means every item is at day's-best level.
- **Test the low end too (same day)**: testing only award sites cannot show whether the ruler also scores ordinary sites high. A template site that never won anything scored 5.3 on the 10 items and 5.64 on the four Awwwards items, clearly below the winners. "Finding the main button within two scrolls" sits at usability 6 as a baseline, and common components on a pure template site get at most 5. The SOTD tested in the same batch (Ciao Energy) was within 0.01 on the four items. The 10 items ran strict because single small flaws cost 1 point; the rule is that single small flaws are noted, not deducted.
- **Run check scripts on real sites**: layout_check.py had only been verified on its own test pages; on 2026-10-13 its first real site produced three kinds of false positives: marquee and carousel cards hidden by their parent counted as "off screen", 40px-tall desktop nav links counted as "tap target too small", and blocked analytics requests counted as "failed to load". The rules: anything clipped by an ancestor does not count, 44px is only checked at phone widths, and only page resources count, ignoring analytics and ads. After the fix the script's own counterexample page still showed all 8 kinds of problems.
- **First real test of anchor calibration (same day)**: two reviewers scoring the same SOTD differed by only 1 point raw (10-item total), far more consistent than the expected ±3. Calibration made things worse that time: the anchor set was full-page screenshots (shrunk to two or three hundred pixels wide for reviewers) while the reference scores came from a separate live browsing session, so whitespace dropped 1 point and motion jumped to 10 (screenshots show no motion; reviewers guessed). The rules: reference scores only come from reviewers looking at the same material; one image per screen; with screenshots only, motion, micro-interactions, usability and retention are not calibrated; each correction is at most ±1, with a warning when it moves a lot.
- **Run the recording script on real sites too (same day)**: record_moment.py crashed twice on its first award site: one selector could not be clicked and the whole recording was lost; a heavy WebGL page timed out on screenshots, also losing everything. A failed step is now noted and recording continues, a timed-out screenshot skips that frame, and recordings and results are saved either way. Most award-site animation is JS (GSAP, WebGL) that the browser's animation API cannot see, so duration is estimated from picture changes (about ±200ms), and anything changing the whole time is marked "looping or scroll-driven"; look at the frames for details.
- **The reference study was tried for real too (same day, on a back-office product behind a login)**: back-office UIs all need a login and cannot be "actually opened", so use official docs and screenshot libraries with sources noted; the 40/30/20/10 on Awwwards detail pages are weights and easily copied as scores; cookie banners block screenshots; a new site has nothing to compare for "find the gaps". See reference-study.md.

# Lessons learned (two redesign rounds of a content site, Oct-Nov 2026)

- **A direction AI reviewers scored high looked ugly to people**: on 10-22 a direction review chose a registry-style look (extra-bold serif headings, numbered record cards, embossed nameplates), and independent review gave it 80.3, 6 points above batch 4's 74.2; after it went live, the people looking found the new version uglier, and in a three-way side-by-side batch 4 was picked again. Before merging and shipping a direction-level redesign, show the user three columns; rejected looks go into "rejected looks", and later review suggestions and direction reviews avoid them.
- **Absolute scores of different batches often differ by three points**: batch 5 scored 3.5 below batch 4 in absolute terms, while both reviewers comparing the two side by side found 8 items better and 0 worse, and 7 better and 1 worse. One reviewer comparing two versions directly is more reliable, so the verdict comes from the blind comparison (calibrate.py votes).
- **A different reviewer model shifts all scores**: three reviews in the second round used one model, the fourth another, and both reviewers said they could not see two animations that were there all along. Record the reviewer model; do not compare absolute scores across models.
- **Reviewers cannot see motion**: a View Transition only gets its name at the moment of the click, so static pages show nothing, and screen recordings drop frames on a busy machine. Motion material for reviewers always comes from record_moment.py on a virtual clock; when a reviewer says "none", check it exists first.
- **One fix pushed the first screen out**: a content page got a hint block with a button, pushing the first result to the bottom edge, and reviewers deducted responsive. Measure key elements' y values every batch (layout_check.py --keep).
- **Reviewers keep raising settled decisions**: splitting tier colors (semantic colors, a look people picked), switching to another method on failure (the project rule is to fail loudly), bumping numbers locally for logged-out users; every round raised them again and every round they had to be explained again. Record "decided not to do" in the brief and strike those items while filtering.
- **Small-memory machines freeze under reviews**: two reviewers each running a headless browser, plus Lighthouse and other sessions, froze the whole machine. Check memory first (macOS sysctl -n hw.memsize, Linux free -g). At 8GB or less, one reviewer at a time with a screenshot cap, and no builds or other browser jobs while they run.
- **Turn a second occurrence into an automated check**: custom component classes sat in a later Tailwind layer, so responsive hiding, height and padding on the same element without ! were silently overridden, twice. A test now parses every className with the TypeScript parser.
- **The user also changes main**: halfway through one polish, the user merged a change on main that duplicated the polish branch (moving a list onto the home page). Pull main before every batch; overlaps follow main.
- **Check speed at kickoff**: all 215 prerendered pages of one content site became per-request renders because the 404 page read request headers, with 1.4 s to first byte. Made static again, it was 0.3 s; that shipped on its own before polishing began.
- **Assemble the best version at the end**: batch 7 (taller first-screen stage, new tier colors) scored below batch 5, and the highest-scored version was to ship. The look followed batch 5; non-visual fixes from batches 7 and 8 (wrapping, tap targets, copy) stayed; the two places batch 7 restyled were edited back to batch 5's look; a full self-check, then release.
- **Do not spend a batch on intermittent local-only errors**: the local production server occasionally returned 404 for background prefetches, reproducible on the pre-redesign version too and absent live; it was recorded as known, and as long as clicking the link really opens, it does not fail.

# Lessons learned (four batches on a booth interaction prototype, Nov 2026)

- **Reviewers cannot hear sound**: given levels for only some sounds, reviewers concluded the keypad, wrong-code and countdown had "no sound", while every button had one. sound_levels.py now clicks every action of the core flow and measures every sound separately, and the level file goes to reviewers; no misjudgment since.
- **Text too small on a scaled canvas**: a 1080-wide booth screen shrunk straight onto a phone turned 28px CSS text into 10px and the top-bar buttons into 32px, and two batches of reviewers called it structural. It passed only after narrowing the logical width on phones and making the visible button size 44px or more; transparent pseudo-elements enlarging the hit area were invisible to reviewers measuring element size. layout_check.py has reported rendered font size since.
- **Splitting dozens of piled-up changes into commits**: 25 changes interleaved in the same few files; one line mixed two changes and adjacent CSS rules could not be separated. Commit each change when it is done.
- **A flow change stalls every old script**: picking a card started advancing automatically, while the screenshot, sound and phone check scripts still clicked "Next" and waited forever for a button the screen had already moved past. After a flow change, rerun every check script.
- **Showing reviewers one color only**: a reviewer asked whether every variant was the same color. Record one sheet per major variant of each signature moment.
- **One segmenter alone breaks CJK words**: the browser segmenter split one word in two and BudouX split another; only break where both agree, and keep short lines on one line when they fit.
- **Removing a layer without replacing it feels empty**: swapping a murky background photo for plain black made both reviewers call it too dark next round; adding large soft light following the theme color brought it back.
- **Generators cap images per run**: 48 base images went out and 4 came back (at most 4 per run), so batch in fours. Put returned images into the real layout before judging them.
- **Work handed off came back untested**: a piece of work was handed off, the executor could not start a browser, and the code came back untested; the main session tested it, replacing a hack that hijacked the browser's audio and a try-catch that swallowed errors. Handed-off work counts only after the main session runs it.

# Lessons learned (second polish round of a campus errand prototype, 82 → 85.5)

- **The check script raised five kinds of false positives on a real site**: all 86 warnings turned out false. Shadow reach was estimated as half the sum of absolute values, larger than reality; place labels faded out of frame were judged by their own opacity, not their ancestors'; 1px screen-reader text counted as truncated; headings split into per-letter inline-blocks at different heights counted as 5 or 6 lines; hit areas enlarged to 48px with `::before` were not measured. layout_check.py now computes shadows per side as blur + spread ± offset and reports pixels past the edge, checks ancestor opacity, skips 1px elements, groups heading lines by half a line height and includes pseudo-element hit areas. A test site with planted problems still reports every real one.
- **Cleaning screenshots deleted the local builds' images**: at wrap-up, screenshots were deleted by extension across the whole work directory with the build folders "skipped", but `find` with `-delete` ignores `-prune`, so several local builds lost their images and a running review saw 404s everywhere. Delete screenshots folder by folder.
- **A later batch scored lower, so the earlier one shipped**: batch 3 (83.0) scored below batch 2 (85.5), so batch 2 shipped with only batch 3's bug fixes moved over, by a replacement script asserting each original snippet occurs exactly once, carrying no look-related change.
- **Stale guide text flashing by**: before a new target appeared, the guide bar still showed the previous step; screenshots only caught the settled state, so it went unnoticed until guide text and highlight were logged every 0.1 s after each click.
- **A panel rendered for only one role**: the desktop lobby's right-hand map only appeared under one role's sorting, leaving the other role an empty column. Screenshot every role and every sort.
- **A feature map missing preconditions**: the map said "the reminder toggle is on the profile page", but it only existed in the wrap-up card after finishing an order, so whoever followed it came up empty. State the preconditions for anything that depends on state.
- **The turn ended when a review came back**: a background review report arrived, got a one-line acknowledgement, and the turn stopped, so the user thought the loop had stopped. Check the review and continue in the same turn.

# Lessons learned (second redesign and release of a food recommendation site)

- **Other deploy sources can roll back a release**: deploy records showed every merged PR auto-deploying the remote branch about twenty seconds later, and a content job deploying from a local working directory every morning. A local deploy pushed to only one of them would be rolled back by the next merge or job. Before shipping, match every deploy source by time and get the code into both the remote branch and that working directory.
- **App screenshots embedded in the site go stale with content**: one dish got a dedicated image, but the result screenshot explaining the flow on the home page and the share image still showed the old one. On reshooting, the result page was a dozen pixels taller and out of line with the other rotating screenshots, so the crop was adjusted back to one height and the annotations remeasured on the new shots.
- **Generic images standing in for specific things**: a dish named as one salad showed a different salad; an article about one soup had a header image that did not show that soup. Both reviewers noticed. Make specific images, spell out the look in the prompt, and add a category to the image rules.
- **Changing a header image tripped a review fingerprint**: the content pipeline fingerprints reviewed sources, so changing the header setting demanded a new review. A build-time overrides table did it instead, sources untouched, quality gates all still passing.
- **A time-dependent greeting broke expected values**: around midnight the home greeting changed and moved a block down by more than twenty pixels, breaking coordinates hard-coded in a fixed test. Expected values became relative positions.
- **Speed scores going up and down**: with below-the-fold styles loaded late, the speed tool sometimes checked accessibility before the styles arrived and reported color contrast. Tested 3 times on the same version, it appeared only once, so it is not a problem.
- **Handed-off acceptance work turned to the user's browser**: an executor that could not start a browser went looking for the user's own browser and desktop-control instructions; others listed files with "key" in their names in the home directory or started a web server open to the local network, all stopped on the spot by the main session watching progress. Prompts say to stop when the browser will not start, and handed-off work is watched.
- **The work directory grew to several GB**: seven batches of review screenshots plus eight frozen production builds. At finish, delete by folder, keeping only original generated images and prompts.

# Lessons learned (second redesign of a pixel puzzle game site)

- **One image 404 in the snapshot**: a small image existed in the working tree but was missed in the commit; reviewers saw the snapshot exported from the commit, so that image was a 404 and scored as fatal. Check the working tree is clean before a snapshot (scripts/snapshot.py) and run the site-wide asset check after (scripts/asset_check.py).
- **Piled-up changes split into the wrong places**: at the end of a batch, splitting zero-context hunks into commits let git apply place several hunks at stale line numbers. Split with 3 context lines (1 when changes are a line or two apart), list every hunk's owner first; a class name several changes shared put one hunk in two items, and only strings unique to one item split it cleanly (scripts/split_commits.py).
- **Reviewers did not see the first-screen demo**: one loop of the demo is about 20 seconds; a reviewer screenshotted at second 0 and second 15, caught the start both times, and concluded the first screen was static. Give looping demos a frame sheet covering a full loop, and state the timeline in the prompt.
- **The scoring script's interface changed mid-round**: the scoring script's arguments and output changed partway, and later batches had to be compared with earlier ones, so the old algorithm had to be kept as a separate copy. Copy the scoring script into the project's work directory at kickoff.
- **The same version differed by 2+ points across rounds**: a version scored 84 in one round scored 82 when re-reviewed at the start of the next. Each new round starts by having that round's reviewers re-score the live version as the base.
- **Category tags collided in the dark theme**: three category tags were distinct in light mode, but two turned into nearly the same dark blue in dark mode. Read actual values for new colors in every theme.
- **A shared footer missed two pages**: a non-breaking space was added to the numbers in the footer; template-generated pages all updated, two hand-written pages did not. After editing shared fragments, grep the whole site for the old text.
- **Rewriting stylesheets through a serializer**: deleting old rules with a CSS parser and writing the whole file back turned `n+3` in a selector into `n/**/+3`, unescaped escaped characters and added a run of blank lines. Delete rules with text edits and read the diff.
- **Wrapping up with the last batch unscored**: the last batch had not been reviewed at wrap-up, so the highest-scored batch shipped; the unscored one was checked and committed on the redesign branch, and live fixes were merged back. The deploy script changed search engine submission records, committed after deploying.
- **Pixel art scaled many times shows seam blocks**: game screenshots scaled 4-5x as posters showed flat colors a few shades apart where base tiles met, as visible rectangles. A high-pass filter exposed the flat areas, and near colors were unified to standard ones.
