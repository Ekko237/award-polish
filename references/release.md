# 上线

## 什么时候上线

- **默认全程本地**：开发、自检、评审都在 localhost 上做，收工条件满足（或到了截止时间）才发布，再在线上完整验证一遍。
- **先部署**：用户或场景要先给一个能访问的链接（交作品要附链接、客户要先看）时，最快上线一个能看的版本占住链接，之后照样全程本地做、中途不更新线上，截止前一次性发布最好的版本。
- **阶段性更新**：只有确定中途有人会看（客户每天看进度、网站已有真实用户），才在本地评审通过（不比线上差、没有致命问题）后更新线上。
- **推送到会自动部署的分支就是上线**（接了 Vercel、Cloudflare 的 main）：用户没点头不推送，点过头的是哪一版就推送哪一版。

## 上线前

- **查清还有谁会部署这个站**：看部署平台最近的记录，按时间对出每个来源（合并 PR 后的自动部署、定时任务从某个工作目录跑的发布脚本、别的会话）。上线的代码要同时进到每个来源用的分支和工作目录，不然下一次合并或定时任务会把线上冲回旧版。
- **记下回滚目标**：当前线上的版本号和回滚命令写进日志。
- 构建必须过；改版还要过 `mode-redesign.md` 的保留检查和品牌检查。

## 最后发布

截止前留出时间：停止开新批，只修问题；把最好的版本推送上线，在线上验证各宽度、核心流程、控制台、图片；有问题在截止前修好，或者退回上一个好版本再推送。线上任何时候都必须是能用的版本。

- **最好的版本怎么拼**：样子以盲比最好的那一批为准；之后不改样子的修正（报错、文案、点击区、可访问性）留着；改了样子又没赢的那几处，用编辑改回最好那一批的样子，整体自检一遍再推送。
- **最后一批还没评分**：上线评分最高的那一批。没评的那批照样检查完、提交在改版分支上，日志里写明它没上线、分支有没有推送到远端。线上分支上做的修正合并回改版分支；合并时资源指纹这类整站跟着变的行会冲突，确认冲突行全是指纹后任取一边，再重跑生成指纹的脚本。
- **部署完看部署用的工作目录**：`git status` 干净才算完。部署脚本改了的状态文件（比如 IndexNow 提交记录）提交并推送，构建留下的缓存目录删掉。

## 上线后

- 用 `wait_live.py <网址> --has <这一版才有的字>` 等线上真的换成新版本（页面和它引用的样式、脚本都查），生效后在线上跑一遍核心流程；有搜索流量的再跑一遍 `seo_keep.py`。
- 给用户看线上时链接带随机参数（`?v=时间戳`）：静态托管（GitHub Pages）会缓存页面约 10 分钟。
- 线上坏了：先把上一个好版本重新推送上去（或用平台的「回到上一个部署」），再修。

## 本地历史带个人信息时只推送干净快照

早期提交用了真名和私人邮箱时：把要上线的提交 `git archive` 导出到公开仓库的克隆里，用公开仓库自己的作者身份提交；推送前 grep 一遍真名、邮箱和不许公开的字样；公开仓库自己的 README、`.nojekyll` 这类文件保留，本地的 `.gitignore` 不放进去。
