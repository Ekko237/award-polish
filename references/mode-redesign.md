# 模式 2：Redesigning an existing website（改版已有网站）

目标：在不破坏已有东西的前提下，把体验提到获奖网站级。
已有的功能、链接、数据都留着。

## 第 1 步：先摸清现状（不重做、不重新盘点功能）

- 拉取最新代码，读一遍代码和已有的日志。
- 打开线上地址，在 375px 和桌面宽度下各截一张图。
- **先查线上快不快**：`curl -sI <网址>` 看 cache-control 和 CDN 命中头（比如 x-vercel-cache、cf-cache-status），`curl -o /dev/null -s -w '%{time_starttransfer}' <网址>` 量首字节，首页和核心页各量三次。全站不走缓存、首字节超过 0.8 秒，算致命问题：查清原因（一个内容资料站的 404 页读了请求头，215 个预渲染页面全变成逐请求渲染，首字节 1.4 秒），单独修、用户点头后单独上线，再开始打磨。
- 先做一份现状审计（借 taste skill 的改版协议），写进日志：
  - 品牌：主色和强调色、字体、圆角、logo 怎么用。
  - 信息架构：页面树、主导航、主要转化路径。
  - 要留的：标志性的交互、认得出的首屏、文案语气。
  - 要去掉的：AI 套路、坏掉的版式、失效链接、廉价图库图、拖慢速度的东西。
  - 现在的三个 dial 读数（装了 design-taste-frontend 时）：这是改版的起点，从这次读数起步。
  - 搜索基线：有排名的页面、每页标题、描述、规范链接、多语言链接、结构化数据类型、H1、分享卡片。用 `scripts/seo_keep.py --base <线上> --new <线上> --pages <页面…> --files /robots.txt /sitemap.xml` 先对线上自己跑一遍（应该 0 处不同），确认脚本能跑、页面清单对，把页面清单写进日志，之后每次发布前拿线上对本地跑。
- 再写清三张清单，记进日志：
  - **必须保留**：域名、路由、产品名、logo（用户没说要换的话）、已有功能、核心流程、用户定过的约束。
  - **可以改**：视觉、版式、动效、文案语气、图片、交互细节。
  - **已经坏了的**：先修。
- 判断改版力度：
  - 请求里是「打磨」「优化」：保留现有风格，往上提。
  - 请求里是「改版」「重做视觉」「推倒重来」：视觉换新，功能、路由、内容保留。
  拿不准就按「保留风格往上提」来，并在日志里写明。
- 功能清单只用来保证**改版时别改坏**。功能已经做完的话，不再补大功能。
- **开工就定的两样，不等评审**（就算这次先不请评审、不看参照站，这两样也当天做完，它们是开工记录的一部分）：
  - 定标卷截图：现在这一版的首页和核心页面，一屏一张（`layout_check.py --slices 8`），1440 和 375 各一组，存进 `refs/anchor/`。标准分可以等第一次请评审时再打，截图开工就截，之后改了代码就截不回来了。
  - 「每项各分数长什么样」：十项各写 6、7、8、9 分的样子，写这个产品自己的东西（页面、按钮、数据）。参照站还没看时先按产品写，看完再补上参照站的例子。
- **现状和待办写到能直接动手**：搜索基线用 `seo_keep.py --base <站> --new <站> --pages <页面…> --dump refs/seo-baseline.json` 存一份字段原文，日志里逐页抄标题和描述的原文、规范链接、结构化数据类型（只写「有」不算），写明改版时这些字段不许变少；待办分致命、体验、打磨三级，每条写位置、问题、改法。

## 第 2 步：看获奖网站，找差距

- 按 `reference-study.md` 挑参照站来看。
- 改版力度是「改版、重做视觉」时，同样先出 2-3 个方向的首屏样张，小评审挑过、用户挑中再动手（做法见 `mode-new.md` 第 2 步）。只是「打磨」就沿用现有方向，不出候选。
- 把我们的首页和核心页面放到它们旁边，按 10 个维度逐项写「我们差在哪」，再按差距从大到小排成待办清单。
- 从核心流程里挑出 4-6 个招牌时刻，写进待办清单。
- 定下（或沿用）间距规范、强调色、圆角、字体，写进日志。全站要统一成这一套。

## 改版从哪下手（「打磨」力度时按这个顺序，够了就停）

1. 字体：风险最小、提升最大。
2. 留白和节奏：拉开 section 间距，理顺上下的节奏。
3. 色彩：降饱和、统一中性色，保留品牌强调色。
4. 动效：给已有组件加合适的微互动。
5. 首屏和关键段重组。
6. 整块换掉：只在现有的那一块救不回来时做。

## 改版专属的两份书面检查（每次发布前写，任何一项不过就不发）

- **保留检查**：列出所有改动过的网址、主导航文字、表单字段名、锚点。应该是空的，除非用户批准过。给搜索引擎看的字段用 `seo_keep.py --base <线上> --new <本地生产构建>` 跑，0 处不同才发。H1 的文字也算搜索字段：改版只改排法，评审建议改 H1、标题、描述的文字，不做（用户批准的除外）。
- **品牌检查**：确认现有的品牌强调色、字体、logo 用法都还在（用户批准换的除外）。

## 第 3 步：进入迭代循环

直接进入 SKILL.md 里共用的「迭代循环」，每批照最新的完整问题清单一口气改完。

改版专属的注意事项：

- **什么时候上线**：照 SKILL.md「全程本地做，弄好了再发布」。网站已经有真实用户时，按那里的「阶段性更新」做，每批都必须完整能用。
- **每批开始前拉一次主分支**：用户自己、或者别的工具也会往主分支上提交（一次改版打磨中途，用户在主分支上合了一个和打磨分支重复的改动）。有新提交就先合进打磨分支，两边做了同一件事的，以主分支的做法为准；合完以后的保留检查拿新的线上当基准。
- **用户连续补充方向时，合并理解**：后一条通常是补充。拿不准就写一份合并后的完整版放进日志，照它执行。

## 网站已经有真实用户时

- **用户数据要兼容**：本地存储的 key 和结构、账号状态、收藏和历史，改版后老用户打开不能丢、不能报错。结构要变就写迁移，并用一份老数据实测。
- **搜索排名别掉**：路由不变；每页的标题、描述、结构化数据、sitemap、canonical 改版前后对照一遍，不许变少。
- **先预览再上线**：用托管平台的预览部署（比如 Cloudflare、Vercel 的预览地址）先在线上环境验证，再切正式；切完马上点一遍核心流程，坏了立刻回滚到上一个部署。
- **CDN 缓存**：除了浏览器缓存，CDN 也会缓存旧页面和旧文件，页面换了、样式文件还是旧的也出过。上线后用 `scripts/wait_live.py <网址> --has <这一版新加的类名或文案>` 确认页面和它引用的样式、脚本都换成新的，必要时清缓存。
- **推送主分支就是上线**：接了自动部署的仓库，推送 main 就是发布，用户点头才推送，推送前跑完保留检查。
- **登录后面的页面**：评审子代理进不去登录墙。先看项目有没有演示模式或测试账号；没有就问用户怎么办，不用用户的真实账号。
