# 打磨清单

## 布局体检（每批都跑）

在 375、768、1024、1280、1440 五档宽度下，首页每个 section 和每个应用页面（包括弹窗、提示、空状态）都要看：

- 有没有一套固定的间距等级（section 间距、块间距、卡片内边距各用哪几个值），全站统一，没有随手写的数值。
- 标题、正文、按钮之间的垂直间距一致。
- 左右边距对齐在同一条线上。
- 首屏不挤也不空；导航一行放得下。
- 底部导航或悬浮按钮不挡内容，最后一块内容留出底部安全距离。
- 文字不溢出、不被裁切；按钮文字不换行。
- 图片比例不变形。
- 没有横向滚动，没有一侧空一大块。

截图用浏览器的视口模拟。无头浏览器有最小宽度限制，375px 的截图可能被裁，不准。

现成脚本在 `<技能目录>/scripts`（`<技能目录>` 的说明见 SKILL.md「脚本放在哪」）：`python3 <技能目录>/scripts/layout_check.py <url...> --widths 375,768,1024,1280,1440 --out <目录>`，一次截完所有宽度并检查溢出、被裁、小于 44px（只在手机宽度查，只报告）、截断、h1 行数、报错和坏图，输出 `report.json`。常用参数：
- `--keep 名字=选择器`（可给多个）：量首屏关键元素的 y 值，不在第一屏、被横幅或浮层盖住都算不过，最后打印一张各宽度的位置表，抄进日志。不同页面的关键元素不同，就分开跑。
- `--states states.json`：操作后的状态（弹窗、选中、展开、各种业务状态）。每个状态写名字、网址和点到那个状态的步骤，脚本在每档宽度点过去再查。
- `--slices 8`：一屏一张截图，给评审和定标卷用。`--forbid` 的值用逗号分隔，写上长破折号（U+2014）、短破折号（U+2013）、Lorem、TODO：页面上不许出现这些字。
- 第一次进站的状态（cookie 横幅、引导弹窗）默认就是被查的那个状态，它们压住主按钮会被 `--keep` 查出来。

## 好用

- 数一数核心流程要点几下，能省的步骤都省：记住上次的选择、默认值、一键再来一次。
- 每页只有一个主要动作，按钮文案就是动作本身。
- 关键信息放在首屏（比如主结果、下一步按钮），不要让用户往下找。加提示条、说明段时先量一下，别把它挤出第一屏。
- 看起来能点的都要能点：写着动作的字（复制、分享、下载）和长得像按钮的东西，点它所在的整块都要有反应。只有其中一小块能点，评审会按「点了没反应」封顶。
- 文案见下面「文案」一节。
- **坏链接也要有交代**：分享链接、邀请链接在聊天软件里常被截掉几个字。解不开、校验不过、字段不对都显示同一个「这一页打不开」的错误页，带一个能继续用的入口；不能白屏，也不能在参数解析处直接报错退出。写一个测试把链接截掉 1、2、3、10 个字和改中间一个字各打开一次。
- **回车和手机键盘的「前往」**：表单最后一个框按回车，必填的都填了就直接提交，没填的跳到空的那个框。
- **空着点提交**：按钮上写清还差什么，空着的框同时标红、抖一下，不能只换按钮上的字。

## 文案

- 标题说具体的事，不说空话：写这个产品能帮谁做成什么，不写「重新定义」「开启新时代」这类套话。
- 按钮写动作本身（「开始测试」「批准修复」），不写「确定」「提交」「了解更多」。
- 同一个东西全站只用一个叫法，术语表写进日志。
- 空状态、报错、等待都要写：空状态告诉用户怎么开始，报错说清发生了什么、下一步怎么办，长等待说清正在做什么。
- 写完整站过一遍 humanizer（中文用 humanizer-zh），去掉 AI 腔、排比、破折号和空话。
- 中英双语的产品，两种语言分别检查长度：英文常比中文长，按钮和标签不能被撑破。

## 好看

- 一个强调色、一套圆角、一套阴影，全站统一。
- **分类色、状态色每种主题都要分得开**：新加几种颜色区分类别（文章分类标签、状态标记）时，浅色和深色主题各取一遍实际底色和字色（`getComputedStyle`），几种底色两两一眼分得开，字的对比度够 4.5:1。只在一种主题下看过不算，深色主题里几种深色很容易撞成一样。
- **中文断行**：标题、卡片短句、画布里排的一句话，只在短语之间断行，不把一个词从中间切开，最后一行不剩一个字。网页文字用 BudouX 在短语之间插 `<wbr>`，配 `word-break: keep-all; text-wrap: balance`；画布里自己排字时，用 BudouX 短语边界和浏览器 `Intl.Segmenter` 分词都认的位置当断点，标点后面最好；短句一行放得下就不折。单靠浏览器分词或按字数切都会切错词。
- **删掉被嫌弃的东西要补上同样有分量的**：评审嫌背景照片发浑，直接换成纯黑，下一轮评审又会说太黑、没气氛。拿掉一层时，用和品牌概念有关的东西补上（跟着主题色变的大面积光、品牌的点阵纹理）。
- 图标和插图风格统一。
- **能用图片就用生成图**：地图底图、插画、场景、装饰、背景、空状态、徽章，一律优先用生图工具生成的图片，不用 SVG、CSS 色块或线条画，SVG 的质感比不上图片。SVG 或 CSS 只用在两处：叠在图片上、需要动或随数据变化的东西（路线动画、高亮点、进度），以及操作类小图标。需要动画的画面就做成「生成图做底 + SVG 动画叠在上面」。每批开工前盘一遍还有哪些画面是画出来的，全部列进清单。
- **图片上叠路线、标记、标签时，先定布局再出图**：生成图里路和楼在哪是随机的，先出图再去猜，叠加层一定对不准。做法：
  1. 先画布局草图：用简单线条和方块定好路网、关键地点、路线。
  2. 把草图当参考图喂给生图工具，要求位置不变，只换成插画或照片质感。
  3. 出图后用程序把位置对上：按颜色识别出路面（或其他承载区域），路线沿真实的路走，标记放在路线上，标签贴着对应的地点。叠加层的位置用排版尺寸算（offsetLeft、offsetTop、clientWidth 这一类），不用 getBoundingClientRect：后者会把 transform 算进去，图片滑入、悬停放大的时候标注就跟着偏。量的时候要等图片加载完、入场动画结束。
  4. 用数字验收，每条都要有数值才算过（只验「在路面上」不够，一个可点原型就栽在这里）：
     - 路线采样点 ≥ 95% 落在路面上。
     - 端点连通：路线起点到起点地点门口、终点到终点地点门口、中转点到前后两段路线，像素距离都 ≤ 8px。
     - 中间不断：相邻采样点间距 ≤ 10px。
     - 起点、终点、中转点完整在画框里，不被裁。
     - 底图铺满画框，四边没有空白或白边。
     - 浮层、标签不压住路线和起点、终点、中转点。
     - 有动画时：用动画结束后的最终画面验收；动画过程中再截 2 张，不能出现「看起来断了」的画面。
     - 地点落在对的东西上：每个地点的点都在对应的物体里或门口 8px 以内，不能落在水、草坪、空地上；类型对得上（每一类地点落在看起来就是那一类的物体上）。
     - 路线不穿越：路线经过的像素 0% 在水面、楼顶、草坪上。路线用程序在路面区域上寻路（比如 A*），距离和「多走几分钟」按寻出来的真实路径算，不按直线算。
     - 镜头会缩放、旋转、平移时，任何时刻画框里都不露出底图边缘或白边（限制镜头范围，或者把底图出得比画框大一圈）。
     - 每种尺寸的图都要过；放大 2 倍截图再看一遍。不合格就重画或微调。
  5. **demo 只求一眼看明白**：同一页上的几张图可以长得不一样，不用拼成同一个世界，也不用工程级精确。每张图按它要讲的那件事单独画草图，元素越少越清楚越好。不能妥协的只有「看得懂」和「没有常识错误」（地点不在水里，路线不穿楼、不穿湖，两头接上，不露白边）。验收用「3 秒测试」：截图交给一个全新的小评审，只看这一张，答出「谁从哪到哪、关键点在哪、为什么」，并且挑不出不对的地方，就算过；上面的数值检查只用来查明显错误。
  6. **全部实例都要过**：一个页面上往往不止一张这样的图（首屏地图、介绍段地图、列表里的小地图、详情页地图、卡片上的路线缩略），每一张都按这套做和验，不能只修被点名的那张。
  这项检查写进每批自检，不要等评审来发现。评审通常只能看到「对不准」这个症状，找不到「先出图后猜位置」这个原因，开发就会反复手动挪坐标。
- **表达内容的图标也算画面**：规则分类、状态（待处理、完成、投诉、隐私）、徽章、加急标记、空状态、底部导航、庆祝效果这些图标，都用生成图，成套出（同一风格、同一尺寸、透明底），和已有生成图标统一。只有**操作符号**保留 SVG 图标库：返回、关闭、勾选、下拉、加减、星级、箭头、搜索、刷新。
- **后台、表格这类信息密集的界面例外**：状态标签（通过、失败、待修复）、表格里的小图标用文字加颜色胶囊或图标库，不用位图，要的是小尺寸下清楚。生成图留给插画、空状态和大块画面。
- **怎么盘点**：每批开工前，在代码里搜 `<svg`、图标库的 import（比如 `@phosphor-icons/react`）、CSS 渐变和画出来的装饰，逐个判断是「操作符号 / 叠加动画」还是「画面」，画面全部列进这批清单。
- 出图顺序：先用生图工具（手头有的都试，额度时有时无）；出不了图就用浏览器里的 ChatGPT、Gemini 或 Grok 网页版（换图规则见 SKILL.md 红线）。
- 数字用等宽数字，金额和分数对齐。

## 流畅

- 切页不闪白、不跳动；骨架屏的形状和真实内容一致。
- 按下有触感反馈（轻微缩放或下沉）；提示不堆叠、不挡内容、按时消失。
- 动效照下面「动效规范」来。
- **切屏不叠影**：新旧两屏同时半透明交叉淡入淡出，两屏的字会叠在一起发脏。离开的屏 100–150ms 快速淡出，进来的屏等 100ms 再淡入（CSS 里给离开状态和进入状态写不同的 transition）。
- 部署后旧缓存导致白屏的情况要防住（加载失败自动刷新、保留上一版打包文件）。

## 动效规范（开工时定，写进日志，全站照用）

获奖站的动效好，靠的是一套统一的节奏。开工时定下这几个值：

- **时长分三档**：按下、悬停这类小反馈 120-180ms；卡片展开、弹窗、提示 200-300ms；切页、大块内容进场 300-450ms。超过 500ms 的只留给招牌时刻，而且不能挡住用户下一步操作。
- **缓动**：进场用减速（ease-out），离场用加速（ease-in），拖动、滑动这类跟手的操作用 spring。全站只用两三条缓动曲线，写成变量。
- **错开**：一组元素一起进场时，每个错开 30-60ms，总时长不超过 500ms。
- **只动 transform 和 opacity**：不动宽高、位置、边距，否则会卡。
- **同一个东西跨页面时连起来**：比如列表里的卡片点开变成详情页，让它从原位置长出来，不要消失再出现。用 View Transitions 做时，只给被点的那一个元素和目标元素起 view-transition-name：列表里每张卡都起名，会让屏幕上所有卡片都被截成单独的图层、按浏览器默认时长淡出，出现叠影。
- **reduced-motion**：用户系统开了「减少动态效果」时，位移和缩放换成淡入淡出，循环动画停掉。
- **怎么验**：每个招牌时刻用 `scripts/record_moment.py` 按虚拟时间逐格截（`--every 40`，给要截的那一步写 `"frames": 800`）。看 `animations.json` 里的时长和缓动是否落在上面三档里，`motion.json` 里画面动了多久，再翻逐格图看过程中有没有跳、断、闪。时间由脚本推进，机器忙不影响结果。

## 细节清单（第一次请评审前、每次发布前各查一遍）

评委和用户会注意到的收尾细节，只看过没过：

- 每个页面的网页标题（浏览器标签上的字）都是这个页面自己的名字。
- 分享卡片：把链接贴进聊天软件时，有标题、一句话介绍和一张专门做的预览图（1200×630）。空白或随便截的图不算。
- 网站图标（favicon）和手机加到主屏的图标都换成自己的。
- 404 页和报错页也按全站风格做，给一个回首页的按钮。
- 桌面端每个能点的东西都有悬停状态，鼠标变成手指；选中文字的颜色、滚动条和全站配色一致。
- 返回上一页时回到离开前的滚动位置；刷新后停在当前页面，不跳回首页。
- 外链在新标签页打开；页面里没有占位文字（Lorem ipsum、TODO、测试数据）。
- **共用片段改完全站搜一遍旧文字**：页尾、页脚、导航这类每页都有的片段，模板生成的页面和手写的页面常常混在一起，生成器只改得到前一种。改完重跑生成器，确认重跑后没有多余改动，再用 grep 搜旧文字，搜到的页面手动改。
- Chrome 和 Safari 各走一遍核心流程（Safari 对模糊、滤镜、粘性定位常有差别）；把动效开到最满，在普通笔记本上看是否掉帧。

## 性能和可访问性（只看过没过；每 3 批、改动涉及图片字体或加载、以及发布前各查一次）

在本地生产构建上测（开发模式的读数不算），手机按限速网络测。Lighthouse 用命令行跑，结果存 JSON 记进日志：

```
npx lighthouse <url> --only-categories=performance,accessibility --output=json --output-path=lh-mobile.json --chrome-flags="--headless"
npx lighthouse <url> --preset=desktop --only-categories=performance,accessibility --output=json --output-path=lh-desktop.json --chrome-flags="--headless"
```


- **Lighthouse**：性能分电脑 ≥ 90、手机 ≥ 80；可访问性 ≥ 90。首屏以下的样式延后加载时，线上测速工具有时在样式到之前就查可访问性，同一版本两次分数不同：每页测 3 次，每次都报的才算问题。
- **首屏出来的速度**：最大内容出现时间（LCP）≤ 2.5 秒。
- **页面不跳**：累计布局偏移（CLS）< 0.1。图片和视频写死宽高比，字体加载时不让文字跳动。
- **图片**：用 WebP 或 AVIF，按显示尺寸出图；首屏单张图不超过约 300KB，首屏以下的图懒加载。生成图出来往往很大，上线前一定压缩。
- **字体**：中文字体只打包用到的字，或者用系统字体；关键字体预加载。
- **键盘**：只用 Tab 和回车能走完核心流程，焦点框看得见，弹窗能用 Esc 关掉。
- **其他**：图片有 alt；按钮和链接有能读出来的名字；文字和背景的对比度达到 WCAG AA。

每一项都记数值，不过就列进这批清单。

## 想回来

- 进度提醒：订单或任务走到哪一步。
- 成长：等级、积分、信用的进度条，以及离下一级还差多少。
- 成就：完成后的小庆祝，要克制。
- 回顾：收入或成果按月、按年汇总。
- 快捷入口：常用任务一键再来。
- **分享出去的那一页也要有招牌时刻**（活动、生成类产品）：别人打开分享链接时，把生成那一下的动画在手机页上重演一遍（等待时成品在暗处隐约可见，别像没加载好，2 秒左右），下面放重播。
- **能存成短视频**：把招牌时刻的画布用 `canvas.captureStream()` 加 `MediaRecorder` 录下来，声音接 `MediaStreamDestination` 一起录；浏览器支持 mp4 就录 mp4，否则 webm；本地文件直接打开时录不了，按钮置灰。
- **分享长图带二维码**：有的社交平台里链接点不了。「分享给朋友」生成一张长图：成品下面接一条邀请短句和这一页的二维码；手机上用 `navigator.share({files})` 直接发图，不支持发图的浏览器就存图并复制链接。用 OpenCV 之类读一遍图里的二维码，确认指向的就是这一页。

## 招牌时刻

从核心流程里挑 4-6 个最关键的瞬间，写进日志，逐个打磨：

- 首屏第一眼
- 核心动作完成的那一下（下单、提交、确认）
- 结果揭晓（码、结果、匹配）
- 价值流动（钱、积分、信用变化），数字滚动和状态变化要看得见
- 页面之间的转场

标准是让人感觉踏实、爽快、想多点两下。为了好看硬加的动效不算达标。

## 操作后的状态也要体检（一个可点原型收工时，人一眼挑出的问题）

- 只截初始示例数据下的静态页面不够。体检要把导览按两种身份完整走一遍，**每一步操作后都截图**；每种业务状态（比如待处理、进行中、待确认、已完成、已取消）在列表和详情都要截到；高亮、选中、展开、弹窗、提示、空状态都算。
- 程序检查除了横向溢出，还要查**被裁掉的描边和阴影**：每个带 border、outline、box-shadow 或圆角的元素，算出含描边和阴影的完整外框，和最近一个 overflow 不是 visible 的祖先的裁剪框比较，超出就记问题。图标超出所在胶囊、标签也照此查。
- 同类元素样式要统一：同一张卡片里的类型标签和状态标签用同一种胶囊；副标题不要重复标题里已有的信息。

## 演示引导要「指哪点哪」（一个可点原型让人亲自走一遍以后定下的做法）

- 给评审或来看演示的人用的原型，引导不能只是一行文字说明。每一步都要直接标出要点的元素（发光描边或光圈加箭头气泡「点这里：发布」），目标不在屏幕里就自动滚过去；切换角色、填写一项、提交打分这种步骤，同样直接高亮对应控件，要填的值写在气泡里。
- 先问再引导：第一次进来弹一个小窗问要不要指引（「带我走一遍」/「我自己逛逛」），接受才开始，拒绝就不打扰；记住选择，并留一个随时能重新开始的「新手指引」入口。不要一进来就强行开始引导。
- 验收：开一个全新子代理，只告诉它「跟着屏幕上的提示走完」，不给任何其他说明，手机版和电脑版各走一遍。中途卡住、不知道点哪，就算不过。
- 逐帧记录指引：每次点击后 2.5 秒里每 0.1 秒记一次指引条的文字、步数和高亮的目标。截图只拍到停稳后的样子，查不出「新目标还没出现、指引条还挂着上一步的话」「光圈先圈住旧按钮再跳走」这种一闪而过的错，用户却每一步都会看到。
- 项目的验证说明里写功能地图时，要靠某个状态才出现的东西写清前提（比如「走完一单后的收尾卡里才有提醒开关，直接打开个人页找不到」），只写一个网址，照着找的人会扑空。

## 手机版和电脑版（演示用的原型）

- 同一个产品、同一份数据，做手机版和电脑版两种界面，不要拆成两个 App，也不要为了演示做「两台手机并排」。
- 让看的人自己选：入口处给两张卡片（各配预览图和一句话），进去后顶部还能随时切换，数据和当前页面不丢；两种界面各有可以单独分享的地址。默认按设备选，但任何设备都能切。
- 电脑版要真的按电脑排版（比如左侧导航、中间列表、右侧详情）。把手机界面放大不算电脑版。在手机上选了电脑版，要能看清，或者提示「电脑上看效果更好」。

## 整块缩放的画面（展位大屏、演示外壳、固定尺寸画布）

整块按固定尺寸设计、再整体缩放的画面（比如 1080×1920 的展位屏，放进电脑的演示外壳或直接在手机上打开），CSS 里的字号和按钮在屏上会被缩小，评审拿手机和笔记本一看就扣响应式、排版和好用程度。
- **手机上按屏幕比例定逻辑宽度**：长屏手机把画面逻辑宽度收窄到约 900（高度照样铺满），同样的字和按钮在手机上大两成；平板和真机照原尺寸。
- **按实际显示的大小验收**：最小字 ≥ 12px、正文 ≥ 14px、能点的东西看得见的大小 ≥ 44px（在缩小的画面上，用透明伪元素扩大点击区不算数，看的人找不到按钮）。`layout_check.py` 报的 `smallText`、`smallTargets`、`smallVisible` 已经按缩放算好，这类画面 `smallVisible` 里的也算不过。
- **电脑演示外壳尽量把屏幕放大**：外壳的装饰（顶盖、边框、底座）越薄越好，1440×900 和 1280×720 下屏幕要够大；窗口矮时两侧说明分开判断放不放得下，只收起放不下的那一侧。
- **手机上去掉对手机没用的东西**：展位屏上的「扫码排队」二维码在手机上扫不了自己，手机上不放；倒计时这类给展位用的规矩，手机上看演示时停掉。

## 批量补的生成素材

- 交回来先和已有素材拼一张对照表看画风是否一致，再**放进真实版式里**看一遍（海报、卡片、背景上有文字的地方）：缩略图看着没问题，构图偏低的图可能压到文字区，真实版式里文字底板挡住了就没事。
- 生成工具一轮能出几张有上限时，按上限分组，交回时按清单核对缺哪几张。
- **图和名字对得上**：每张配图要画的就是旁边写的那样东西。写着芝士汉堡的不能配鸡肉卷，文章讲手冲咖啡的头图里要看得见手冲壶；拿一张通用图顶替，评审会按「不真」扣分。出图提示词里写死这样东西的长相（形状、配料、不要什么），交回后逐张对名字看一遍。图库里只有通用图时，补专门的图，再改配图规则让它用上。
